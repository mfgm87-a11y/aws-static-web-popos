Fundamentos · 44%

La idea que explica todo lo demás

Kubernetes no recibe órdenes paso a paso. Tú le dices cómo quieres que se vean las cosas, el estado deseado, y él se encarga de que la realidad coincida. Si algo se desvía, lo corrige solo.

  • Declarativo es describir el resultado (el YAML). Imperativo es dar los pasos uno por uno. Kubernetes es declarativo.
  • Casi todo en Kubernetes es un controller haciendo este bucle: el Deployment, el Job, el autoescalado.
  • Por eso se dice que Kubernetes se "autorrecupera". No es magia: es un bucle que corrige diferencias todo el tiempo.
Fundamentos · 44%

Quién hace qué dentro del cluster

Un cluster tiene dos partes: el control plane, que decide, y los nodos worker, que ejecutan. La regla que más preguntas resuelve: todos los componentes hablan solo con el API server. Nadie habla directo con nadie más.

ComponenteQué haceFrase para el examen
Control plane
kube-apiserverPuerta de entrada. Recibe, valida y guarda cada petición.Todo pasa por el API server.
etcdBase de datos clave-valor con todo el estado del cluster.Solo el API server habla con etcd. Se corre en número impar (3 o 5) para tener quórum.
kube-schedulerMira los pods sin nodo y elige dónde ponerlos: filtra los nodos que sirven y les da puntaje.Decide dónde. No decide cuándo y no arranca nada.
kube-controller-managerCorre los controllers: Deployment, ReplicaSet, Job, CronJob, Node.Corrige la diferencia entre deseado y real.
cloud-controller-managerConecta con la nube: balanceadores, discos, máquinas.Solo existe si corres en una nube.
En cada nodo
kubeletRecibe los pods asignados a su nodo y se asegura de que corran y estén sanos.El agente del nodo. Le habla al runtime por CRI.
kube-proxyPrograma reglas de red (iptables por defecto, o nftables; el modo IPVS está obsoleto desde v1.35) para que el tráfico a un Service llegue a algún pod.Enruta. No cifra.
containerd / CRI-OEl runtime: descarga imágenes y corre los contenedores.Kubernetes ya no usa Docker como runtime, pero las imágenes de Docker siguen sirviendo porque son OCI.
Trampa

El kube-scheduler no tiene nada que ver con horarios. Aquí "scheduling" es asignar un pod a un nodo. Lo que corre cosas a una hora fija es el CronJob.

Fundamentos · 44% · pregunta 03 del simulador

Qué pasa cuando corre un CronJob

Este recorrido es el cluster entero trabajando junto. Fíjate en dos cosas: cada paso lo da un componente distinto, y ninguno le habla directo al siguiente. Todos escriben y leen en el API server.

  1. 1
    CronJob controllerdentro del controller-manager
    Llega la hora. Crea un objeto Job.
  2. 2
    Job controllerdentro del controller-manager
    Ve el Job nuevo y crea un Pod.
    Pod: Pending, sin nodo
  3. 3
    kube-schedulercontrol plane
    Ve un pod sin nodo, evalúa los nodos y anota en el API server en cuál va. No arranca nada.
  4. 4
    kubeletdel nodo elegido
    Ve que le asignaron un pod y le pide al runtime que lo arranque.
  5. 5
    containerdruntime del nodo
    Descarga la imagen si no la tiene y corre el contenedor.
    Pod: Running
  6. 6
    Finla tarea termina bien
    El contenedor sale sin error. El pod queda Succeeded y el Job queda Complete.
Respuesta: D

El CronJob crea un Job, y el Job crea el Pod. Los objetos grandes delegan en cadena, igual que el Deployment, que crea un ReplicaSet que crea los Pods.

  • A está mal: el kubelet no mira CronJobs. Solo mira los pods asignados a su nodo.
  • B está mal: el scheduler no maneja horas. Su "scheduling" es escoger nodo.
  • C está mal: se salta el Job. El CronJob nunca crea pods directamente.

Los objetos y quién crea a quién

El Pod es la unidad mínima de Kubernetes: uno o más contenedores que comparten IP y discos, y que viven y mueren juntos. Casi nunca lo creas a mano. Lo crea un controller que lo cuida por ti.

Si necesitas…UsasEjemplo
App sin estado, copias intercambiablesDeploymentAPI web, frontend
App con estado: cada copia con nombre fijo y su discoStatefulSetBase de datos, Kafka
Un pod en cada nodoDaemonSetRecolector de logs, agente de monitoreo
Tarea que corre y terminaJobMigración de datos
Tarea que se repite a una horaCronJobReporte cada noche

Otros objetos que salen siempre

Service

Dirección fija (IP y nombre) para un grupo de pods que cambian todo el tiempo. Ver Red.

Ingress

Entrada HTTP/HTTPS desde afuera del cluster, por dominio y ruta. Necesita un ingress controller instalado.

ConfigMap

Configuración separada del código: URLs, parámetros. El pod la lee como variables de entorno o como archivo.

Secret

Igual que ConfigMap, pero para contraseñas y llaves. Van en base64, y base64 no es cifrado: por defecto se guardan sin cifrar en etcd.

Namespace

Carpetas lógicas dentro del cluster. Vienen por defecto: default, kube-system, kube-public, kube-node-lease.

Labels y selectors

Etiquetas clave=valor (app=web). Así un Service o un Deployment encuentra "sus" pods.

Annotations

Notas para herramientas (ej. qué emisor usa cert-manager). No sirven para seleccionar objetos.

CRD

Custom Resource Definition: te deja crear tipos de objeto nuevos. Así funciona el Certificate de cert-manager.

Operator

Un controller propio que usa CRDs para manejar una app compleja (instalar, escalar, hacer backups) como lo haría una persona experta.

Trampa

"Container" no es un objeto de Kubernetes. No existe kind: Container. La unidad desplegable más pequeña es el Pod.

Fundamentos · 44%

El Pod por dentro: fases, probes y reinicios

Un Pod pasa por pocas fases y el examen pregunta mucho por ellas. La clave: la fase es del Pod, pero los reinicios son de cada contenedor, y los hace el kubelet según la restartPolicy.

FaseQué significa
PendingAceptado, pero todavía no corre: espera nodo (scheduler) o está descargando la imagen.
RunningYa tiene nodo y al menos un contenedor está corriendo, arrancando o reiniciando.
SucceededTodos los contenedores terminaron bien (código 0) y no se van a reiniciar. Típico de un Job.
FailedTodos terminaron y al menos uno falló (código distinto de 0).
UnknownNo se sabe el estado, casi siempre porque se perdió el contacto con el nodo.
Trampa

CrashLoopBackOff, ImagePullBackOff u OOMKilled no son fases. Son estados o motivos de un contenedor; mientras tanto, el Pod sigue en Pending o Running.

Las tres probes

ProbePregunta que haceSi falla…
liveness¿Sigue vivo o se colgó?El kubelet reinicia el contenedor.
readiness¿Ya puede recibir tráfico?Lo saca de los endpoints del Service. No lo reinicia.
startup¿Ya terminó de arrancar?Las otras dos esperan hasta que pase. Sirve para apps lentas al arrancar.

Se configuran con httpGet, tcpSocket, exec o grpc. Una liveness mal configurada (por ejemplo, con la ruta equivocada) reinicia una y otra vez una app que está sana.

restartPolicy y contenedores especiales

  • restartPolicy va en el Pod: Always (por defecto, y la única válida en Deployments), OnFailure o Never (las que usan los Jobs).
  • Init containers: corren uno por uno y cada uno debe terminar bien antes de que arranque la app. Sirven para preparar cosas o esperar dependencias.
  • Sidecars nativos (estables desde v1.33): un init container con restartPolicy: Always. Arranca antes que la app y la acompaña toda su vida; típico para proxies o recolectores de logs.
  • Apagado: al borrar un Pod, el kubelet manda SIGTERM, espera el periodo de gracia (30 s por defecto) y después manda SIGKILL.
Fundamentos · 44%

Contenedores e imágenes

Un contenedor no es una máquina virtual: es un proceso aislado que comparte el kernel del host. El aislamiento lo dan dos funciones del kernel de Linux: los namespaces (lo que el proceso puede ver) y los cgroups (cuánto puede consumir).

ContenedorMáquina virtual
KernelComparte el del hostTrae el suyo
ArranqueMuy rápido, segundos o menosMás lento, suele tardar minutos
AislamientoMás livianoMás fuerte

La imagen

  • Una imagen son capas de solo lectura más un manifiesto y una configuración. Al arrancar, el runtime pone encima una capa escribible que se pierde al reiniciar. Lo que debe durar va en volúmenes.
  • Referencia: registro/repositorio:tag. Si no pones registro, se asume Docker Hub. El tag se puede mover a otra imagen; el digest (@sha256:…) apunta siempre al mismo contenido.
  • Sin tag (o con :latest) la política de descarga por defecto es Always; con cualquier otro tag es IfNotPresent.
  • Registro privado: un Secret de tipo dockerconfigjson que se referencia en imagePullSecrets.

El Dockerfile en cuatro ideas

ENTRYPOINT y CMD

ENTRYPOINT es el ejecutable; CMD, los argumentos por defecto. En Kubernetes, command reemplaza al ENTRYPOINT y args al CMD.

RUN

Se ejecuta al construir la imagen, no al arrancar el contenedor.

Multi-stage

Compilas en una etapa con todas las herramientas y copias solo el resultado a una imagen mínima (distroless o scratch). Queda más pequeña y más segura.

Secretos

Nunca en ENV ni en COPY: quedan guardados en las capas aunque los borres en un paso posterior.

Quién corre los contenedores

kubelet→ CRI →containerd o CRI-O→runc (OCI)→proceso aislado
  • OCI define los estándares de imagen, de runtime y de distribución. Por eso una imagen hecha con Docker corre en containerd.
  • Kubernetes quitó el dockershim en v1.24: Docker Engine ya no es un runtime directo, pero sus imágenes siguen sirviendo.
  • RuntimeClass deja elegir un runtime con más aislamiento, como gVisor o Kata Containers.
Orquestación · 28%

Cómo llega el tráfico a tu app

Los pods nacen y mueren cambiando de IP. Por eso nunca se les habla directo: se les habla a través de un Service, que tiene IP y nombre fijos y reparte el tráfico entre los pods que tengan la etiqueta correcta.

Tipo de ServicePara qué
ClusterIPEl tipo por defecto. Solo se alcanza desde dentro del cluster.
NodePortAbre un puerto (rango 30000–32767) en cada nodo para entrar desde afuera.
LoadBalancerLe pide a la nube un balanceador con IP pública.
ExternalNameUn alias DNS hacia un servicio que está fuera del cluster.
HeadlessclusterIP: None. Sin IP fija: devuelve la IP de cada pod. Lo usa el StatefulSet.

CoreDNS

El DNS del cluster. Nombre completo de un Service: mi-svc.mi-namespace.svc.cluster.local

CNI

Un estándar, no una herramienta. Define cómo los plugins de red (Calico, Cilium, Flannel) le dan IP y conectividad a los pods.

NetworkPolicy

Firewall entre pods. Solo funciona si el plugin CNI la soporta.

Gateway API

La evolución de Ingress: más completa y con roles separados. Si la ves como opción para "exponer tráfico", es válida.

Service mesh

Istio o Linkerd. Ponen un proxy junto a cada pod (Envoy en Istio; en su modo ambient, un proxy por nodo): cifrado mTLS, reintentos y métricas sin tocar el código.

Envoy

Proxy de capa 7 de la CNCF. Sirve de puerta de entrada (edge) y de sidecar entre servicios.

Trampa

Por defecto, en Kubernetes todos los pods pueden hablar con todos. Si una pregunta habla de restringir tráfico entre pods, la respuesta es NetworkPolicy. Si habla de cifrar tráfico entre servicios, es mTLS con un service mesh. Nunca kube-proxy.

Orquestación · 28%

Seguridad básica

KCNA pregunta seguridad a nivel de conceptos. El KCSA va a profundizar en todo esto, así que lo que aprendas aquí te sirve dos veces. Empieza por el recorrido de cualquier petición al API server:

Petición→Autenticación: ¿quién eres?→Autorización (RBAC): ¿puedes?→Admission: ¿cumple las reglas?→Se guarda en etcd

Las 4C

Cloud → Cluster → Container → Code. Capas de seguridad; cada una protege a la de adentro.

RBAC

Role (permisos en un namespace) o ClusterRole (en todo el cluster). El RoleBinding o ClusterRoleBinding se lo asigna a alguien. Permisos = verbos (get, list, create, delete) sobre recursos.

ServiceAccount

La identidad de un pod frente al API server. Las personas son users; los pods usan service accounts.

Mínimo privilegio

Dar solo los permisos necesarios. Si una opción da permisos de más "por si acaso", está mal.

Secrets

Base64 no es cifrado. Para cifrarlos dentro de etcd hay que activar encryption at rest.

Pod Security Standards

Tres niveles: Privileged, Baseline, Restricted. Los aplica el Pod Security Admission, que reemplazó a PodSecurityPolicy.

Admission controllers

Revisan o modifican peticiones antes de guardarlas. Para políticas propias: OPA Gatekeeper o Kyverno.

cert-manager

Certificados TLS automáticos para apps. Cadena: Issuer → Certificate → Secret → Ingress. Los renueva solo.

Fundamentos + Orquestación

Recursos, escalado, discos y fallas

Recursos y scheduling

  • requests: lo que el pod reserva. El scheduler lo usa para escoger un nodo con espacio.
  • limits: el máximo. Si pasa el límite de memoria, lo matan (OOMKilled). Si pasa el de CPU, lo frenan, pero no lo matan.
  • QoS: Guaranteed (requests = limits), Burstable (tiene algo), BestEffort (no tiene nada; es el primero en morir si falta memoria).
  • Taints y tolerations: el taint va en el nodo y repele pods; la toleration va en el pod y le deja entrar.
  • nodeSelector y affinity: el pod pide ir a ciertos nodos (ej. los que tienen GPU).
  • PriorityClass: los pods importantes se programan primero y, si no caben, el scheduler puede desalojar (preempt) pods de menor prioridad.
  • Repartir réplicas: pod anti-affinity o topology spread constraints, para que un nodo o una zona caída no tumbe todas las copias.

Escalado

HerramientaQué escalaDetalle
HPAMás o menos podsSegún métricas como CPU. Necesita metrics-server.
VPAPods más grandes o más chicosAjusta los requests de CPU y memoria.
Cluster AutoscalerMás o menos nodosSe activa cuando hay pods en Pending por falta de espacio. Karpenter es una alternativa.

Almacenamiento

  • Volume: disco del pod. Un emptyDir se borra cuando muere el pod.
  • PersistentVolume (PV): el disco real. PersistentVolumeClaim (PVC): la solicitud del pod ("necesito 10 GB").
  • StorageClass: crea el PV automáticamente cuando llega un PVC. Esto se llama aprovisionamiento dinámico.
  • CSI: el estándar para conectar proveedores de almacenamiento.
  • Modos de acceso: ReadWriteOnce (un nodo escribe), ReadOnlyMany, ReadWriteMany (varios nodos escriben), ReadWriteOncePod.

Versiones y actualizaciones

  • Sale una versión menor unas tres veces al año, y cada una recibe parches durante unos 14 meses.
  • Se actualiza primero el control plane y después los nodos, de a una versión menor (1.36 → 1.37), sin saltar.
  • Regla de versiones: el kubelet puede ir hasta tres versiones menores detrás del API server, pero nunca adelante.
  • APIs: alpha (apagada por defecto, puede desaparecer), beta (todavía puede cambiar; las nuevas vienen apagadas desde v1.24) y estable (v1, para producción).

Límites por namespace

ResourceQuota

Tope para todo el namespace: CPU y memoria totales, número de pods, PVCs, ConfigMaps… Si hay cuota de CPU, cada pod debe declarar sus requests.

LimitRange

Valores por defecto y mínimos o máximos para cada contenedor. Rellena los requests que falten.

PodDisruptionBudget

Cuántas réplicas pueden caer a la vez en interrupciones voluntarias, como un drain. No protege si el nodo se cae solo.

Trampa

cordon no mueve nada: solo evita pods nuevos. drain hace el cordon y además desaloja los pods. Y kubectl scale fija las réplicas, mientras que kubectl autoscale crea un HPA.

Entrega de aplicaciones · 16%

Cómo depurar sin perderte

Depurar en Kubernetes es seguir siempre el mismo orden: qué dice el objeto, qué dice la app y, solo al final, entrar a mirar.

  1. 1
    kubectl getel estado
    ¿Pending, CrashLoopBackOff, READY 1/2? El estado ya te dice dónde buscar.
  2. 2
    kubectl describelos Events
    Scheduling fallido, imagen que no baja, probe que falla, OOMKilled, y el motivo y código de salida del último reinicio.
  3. 3
    kubectl logsla app
    Lo que imprimió la app. Con --previous ves la ejecución anterior a un reinicio; con -c, otro contenedor del pod.
  4. 4
    kubectl exec o debugentrar
    exec si la imagen tiene shell. Si es distroless, kubectl debug agrega un contenedor efímero con herramientas, sin reiniciar el pod.
Código de salidaQué suele significar
0Terminó bien.
1Error de la aplicación.
127Comando no encontrado: el shell no halló el binario.
137128 + 9: lo mataron con SIGKILL, casi siempre por OOM.
143128 + 15: recibió SIGTERM, un apagado normal.

port-forward

kubectl port-forward svc/web 8080:80 abre un túnel temporal desde tu máquina. No expone nada al público.

Pod temporal

kubectl run tmp --rm -it --image=busybox -- sh para probar DNS o conectividad desde dentro del cluster. Se borra al salir.

Depurar un nodo

kubectl debug node/<nodo> -it --image=busybox crea un pod en ese nodo con su sistema de archivos en /host. Sin SSH.

Rollout

kubectl rollout status sigue un despliegue y kubectl rollout undo vuelve atrás. Con Helm: helm history y helm rollback.

Trampa

Si la app responde dentro del pod pero no a través del Service, casi nunca es la app: revisa que el selector del Service coincida con las labels, que haya endpoints, que el targetPort sea el correcto y que la app escuche en 0.0.0.0 y no solo en 127.0.0.1.

Arquitectura cloud native · 12%

Principios, observabilidad y comunidad

Cloud native es una forma de diseñar, no una herramienta. La CNCF lo define como sistemas desacoplados, resilientes, manejables y observables que, con automatización, permiten hacer cambios frecuentes y predecibles con poco esfuerzo.

  • Características: resiliencia, agilidad, operabilidad, observabilidad, disponibilidad. Son cualidades. Una opción que mezcla un nombre de herramienta se descarta.
  • Microservicios vs monolito: muchos servicios pequeños que se despliegan por separado, contra una sola aplicación grande.
  • Serverless: no administras servidores y puede escalar a cero. En Kubernetes: Knative.
  • FinOps: visibilidad, optimización y pronóstico de costos, de forma automatizada. Herramienta CNCF: OpenCost.
  • SLI, SLO, SLA: SLI es la medida (% de peticiones exitosas). SLO es la meta interna (99,9%). SLA es el compromiso con el cliente, con consecuencias si no se cumple.

Cómo se conecta la red de los pods.

Cómo se conecta el almacenamiento.

Comunidad

  • La CNCF, parte de la Linux Foundation, aloja Kubernetes y cientos de proyectos más.
  • Niveles de madurez de un proyecto: Sandbox → Incubating → Graduated. Los decide el TOC (Technical Oversight Committee).
  • Kubernetes se organiza en SIGs (Special Interest Groups) por tema: SIG Network, SIG Storage, SIG Security.
  • Los cambios grandes se proponen como KEP (Kubernetes Enhancement Proposal). Salen tres versiones al año.

Reglas que resuelven preguntas

  1. ¿Herramienta o concepto? Si piden una característica o un recurso, descarta los nombres de herramientas (kubectl, containerd).
  2. Manual contra automatizado: casi siempre gana automatizado.
  3. La unidad mínima es el Pod, no el contenedor.
  4. kubectl run crea un Pod. kubectl create deployment crea un Deployment. Las copias siempre son --replicas.
  5. El scheduler decide el nodo, nunca la hora.
  6. Todos hablan con el API server, y solo él habla con etcd.
  7. kube-proxy enruta, no cifra. Cifrado entre servicios = mTLS del service mesh.
  8. Secret es base64, que no es cifrado.
  9. Por defecto todos los pods se hablan. Para restringir: NetworkPolicy.
  10. /var/log son logs. /etc es configuración.
  11. Sin estado → Deployment. Con estado → StatefulSet. En cada nodo → DaemonSet. Tarea → Job o CronJob.
  12. Si una opción suena bien pero tiene una palabra que la mata ("manual", "directamente", "siempre", "solo"), léela otra vez.

83¿Cuál es la unidad desplegable más pequeña en Kubernetes?▸
PodMarcaste: Container

El contenedor es del runtime, no un objeto de Kubernetes. Kubernetes programa y despliega pods.

41¿Cuáles son las características de una app cloud native? (2)▸
Las dos listas sin nombres de herramientasMarcaste solo una de las dos

Resiliencia, agilidad, operabilidad, observabilidad, disponibilidad. Las opciones con containerd o Kubernetes se descartan porque son herramientas.

126¿Comando para un Deployment de nginx con 2 réplicas?▸
kubectl create deploy nginx --image=nginx --replicas=2Marcaste: --count=2

--count no existe. kubectl run solo crea pods.

243¿Cómo entrega cert-manager certificados TLS a una app?▸
Maneja recursos Certificate y Secrets que usa el IngressMarcaste: actualiza kube-proxy para cifrar

kube-proxy solo enruta. cert-manager guarda el certificado en un Secret y el Ingress lo usa.

193¿Qué recurso maneja una app sin estado?▸
DeploymentMarcaste: kubectl

kubectl es la herramienta, no un recurso. StatefulSet es para apps con estado; DaemonSet, uno por nodo.

197¿Qué proxy de borde y de servicio está hecho para apps cloud native?▸
EnvoyMarcaste: gRPC

gRPC es un protocolo de comunicación. Envoy es el proxy, el sidecar que usa Istio.

160¿Buen hábito para la eficiencia de costos cloud native?▸
Optimización automatizada, con visibilidad y pronósticoMarcaste: procesos manuales

Eso es FinOps. En cloud native lo manual llega tarde porque los recursos cambian todo el tiempo.

Ni el kubelet ni el scheduler miran CronJobs. Ver el recorrido completo en CronJob.
