Panorama · 14%

La idea: capas y mínimo privilegio

Ningún control basta por sí solo. La seguridad cloud native apila capas independientes (defensa en profundidad) para que, si una falla, las otras sigan conteniendo el daño. El modelo más preguntado son las 4C: cada capa se apoya en la de afuera.

Mínimo privilegio

Cada persona y cada carga recibe solo los permisos que necesita. Si una opción da permisos de más "por si acaso", está mal.

Zero trust

Nunca confíes, siempre verifica: estar dentro de la red no da confianza. Cada llamada se autentica y se autoriza, por ejemplo con mTLS.

Separación de funciones

Ninguna identidad sola puede hacer todos los pasos críticos. Quien escribe las políticas no es quien despliega.

Responsabilidad compartida

En un servicio gestionado, el proveedor protege el control plane. Tus cargas, tu RBAC, tus imágenes y tus Secrets siguen siendo tuyos.

Las fases del ciclo de vida

La documentación oficial y el whitepaper de seguridad de la CNCF también ordenan los controles por fases:

FaseControles típicos
DevelopCódigo seguro, revisión, análisis estático (SAST) y de dependencias (SCA)
DistributeEscaneo de imágenes, firma, SBOM, procedencia, registro privado
DeployPolíticas de admisión: Pod Security, verificar firmas, registros permitidos
RuntimeAcceso, red, almacenamiento, detección (Falco), auditoría

Tipos de control

  • Preventivo: impide que pase. Ejemplo: la admisión rechaza un pod privilegiado.
  • Detectivo: avisa que pasó. Ejemplo: Falco alerta de una shell dentro de un contenedor.
  • Correctivo: arregla después. Ejemplo: restaurar etcd desde un backup.
  • Compensatorio: reemplaza a un control que no puedes aplicar. Ejemplo: una app que debe correr como root va en nodos dedicados, con NetworkPolicy estricta y más monitoreo.
Fundamentos de seguridad · 22%

El recorrido de una petición al API server

Todo pasa por el API server, y toda petición cruza tres puertas, siempre en este orden. Si entiendes qué revisa cada puerta, resuelves media sección del examen.

Puerta 1: autenticación

MétodoCómo funciona
Certificado X.509El CN del certificado es el usuario y cada O es un grupo. No se pueden revocar: uno filtrado sirve hasta que vence.
OIDCUn proveedor de identidad (Entra ID, Okta, Keycloak) entrega tokens de corta duración. Lo correcto para personas.
ServiceAccountIdentidad de los pods: system:serviceaccount:<ns>:<nombre>. Tokens cortos de la API TokenRequest. Un ServiceAccount por app, no el default.
Bootstrap tokenToken corto para que un nodo nuevo pida su certificado (TLS bootstrapping). Solo para unir nodos.
AnónimoSi está activo, quien no se identifica pasa como system:anonymous. Nunca darle permisos.

Kubernetes no tiene un objeto User: las personas vienen de afuera (certificados u OIDC). Los ServiceAccounts sí son objetos.

Puerta 2: autorización

  • La configuración estándar es --authorization-mode=Node,RBAC. AlwaysAllow en cualquier posición deja pasar todo.
  • RBAC solo suma: no hay reglas de denegar. Si cualquier binding lo permite, está permitido.
  • Un RoleBinding que usa un ClusterRole da esos permisos solo en su namespace.
  • El autorizador Node y la admisión NodeRestriction limitan a cada kubelet a lo de su propio nodo.
  • El grupo system:masters se salta RBAC por completo y no se le pueden quitar permisos borrando bindings.

Permisos que parecen inocentes y no lo son

PermisoPor qué es peligroso
create podsPuede montar cualquier Secret y usar cualquier ServiceAccount del namespace.
list / watch secretsLa respuesta trae el contenido completo: es lo mismo que leerlos.
escalateCrear o editar roles con más permisos que los propios.
bindAsignar roles que uno mismo no tiene.
impersonateActuar como otro usuario o grupo, incluso uno privilegiado.
create serviceaccounts/tokenSacar tokens de cualquier ServiceAccount del namespace.
get nodes/proxyLlega a la API del kubelet: permite exec en cualquier pod del nodo, sin auditoría ni admisión.
aprobar CSRsEmitir certificados con cualquier identidad, incluso system:masters.
webhook configurationsVer y modificar cada objeto que entra al cluster.

Puerta 3: admisión

  • Orden fijo: primero los mutantes (cambian el objeto), luego la validación del esquema y al final los validantes. Así la validación ve el objeto final.
  • failurePolicy: Fail: si el webhook se cae, se rechaza (seguro, pero puede bloquear despliegues). Ignore: se admite sin revisar (disponible, pero un atacante que tumbe el webhook se salta la política).
  • Motores de políticas: OPA Gatekeeper (Rego), Kyverno (YAML) y ValidatingAdmissionPolicy (CEL, integrada y estable desde v1.30).
Componentes del cluster · 22%

Cada componente: qué se arriesga y cómo se protege

Para cada pieza del cluster, el examen pregunta lo mismo: ¿qué ganaría un atacante si la controla? y ¿qué ajuste la protege?

ComponenteRiesgo y protección
Control plane
kube-apiserverRiesgo: Es la puerta a todo el cluster.
Se protege con: Sin anónimo con permisos, Node,RBAC, endpoint privado, auditoría, API Priority and Fairness contra la saturación.
etcdRiesgo: Escribir ahí se salta autenticación, autorización y admisión. Tiene todos los Secrets.

kube-schedulerRiesgo: Podría poner pods donde quiera o dejar de programarlos.

En cada nodo
kubeletRiesgo: Su API (10250) permite ejecutar comandos en los contenedores.
Se protege con: anonymous-auth=false, autorización Webhook, puerto de solo lectura 10255 apagado, NodeRestriction.

kube-proxyRiesgo: Podría redirigir el tráfico de los Services. Corre privilegiado.

Alrededor

Fundamentos de seguridad · 22%

Endurecer los Pods

Kubernetes trae tres niveles de seguridad para pods, los Pod Security Standards, y un controlador integrado que los aplica por namespace, el Pod Security Admission. Reemplazó a PodSecurityPolicy, que se eliminó en v1.25.

NivelQué exige
PrivilegedNada. Para cargas de sistema de confianza (CNI, agentes de almacenamiento).
BaselineProhíbe lo obviamente peligroso: privileged, hostNetwork, hostPID, hostIPC, volúmenes hostPath, hostPort, capabilities fuera de una lista segura y seccomp Unconfined.
RestrictedTodo Baseline y además: runAsNonRoot: true, allowPrivilegeEscalation: false, drop: [ALL] (solo se puede devolver NET_BIND_SERVICE), seccomp RuntimeDefault o Localhost y solo ciertos tipos de volumen.

Cómo se aplica

  • Con labels en el namespace: pod-security.kubernetes.io/<modo>=<nivel>.
  • Tres modos: enforce (rechaza), audit (deja pasar y anota el evento de auditoría) y warn (deja pasar y avisa al usuario). Se pueden combinar, por ejemplo enforce=baseline y warn=restricted.
  • enforce revisa Pods, no Deployments: el Deployment se crea, pero su ReplicaSet no logra crear los pods y el error sale en sus eventos.
  • Un namespace sin labels queda en privileged, salvo que el admin ponga valores por defecto en la configuración del plugin.
  • Para probar sin romper nada: kubectl label --dry-run=server --overwrite ns prod pod-security.kubernetes.io/enforce=restricted muestra qué pods fallarían.
  • Quien puede editar el objeto Namespace puede bajar su nivel: ese permiso es sensible.

El securityContext que más se pregunta

AjusteQué hace
runAsNonRoot: trueEl kubelet no arranca el contenedor si iba a correr como UID 0.
allowPrivilegeEscalation: falseActiva no_new_privs: los binarios setuid como sudo no sirven para escalar.
capabilities: drop [ALL]Quita los poderes especiales de root, como NET_RAW (paquetes falsos) o SYS_ADMIN (casi todo).
readOnlyRootFilesystemNadie puede cambiar binarios ni dejar herramientas en el contenedor.
seccompProfileRuntimeDefault filtra llamadas al sistema peligrosas.
hostUsers: falseUsa user namespaces (estables desde v1.36): root dentro del contenedor no es root en el nodo.
automountServiceAccountToken: falseNo monta el token si la app no usa la API.

Aislar más fuerte

  • Un namespace no es una frontera fuerte: los pods comparten nodos, kernel y red.
  • Para código no confiable: nodos dedicados (taints, tolerations y afinidad) y un runtime con sandbox vía RuntimeClass. gVisor pone un kernel en espacio de usuario; Kata Containers, una micro-VM por pod.
  • De menor a mayor aislamiento: namespace, cluster virtual (como vcluster), cluster separado.
  • seccomp filtra llamadas al sistema; AppArmor usa perfiles por ruta; SELinux usa etiquetas.
Trampa

privileged: true más hostPID: true es la receta clásica de escape: desde el pod, nsenter --target 1 --mount --uts --ipc --net --pid -- bash da una shell root en el nodo. Baseline prohíbe las dos.

Fundamentos de seguridad · 22%

Secretos y auditoría

Un Secret no es secreto por defecto: los valores van en base64 (que se decodifica con un comando) y se guardan sin cifrar en etcd. Protegerlo es trabajo tuyo.

  • Quien puede crear pods en un namespace puede leer sus Secrets: monta uno e imprime su contenido.
  • Mejor montarlos como archivo que como variable de entorno: las variables se filtran a logs y a procesos hijos.
  • immutable: true evita cambios accidentales y le quita carga al API server.
  • Para Git: Sealed Secrets o SOPS los guardan cifrados. Para no guardarlos en el cluster: External Secrets Operator o el Secrets Store CSI Driver con Vault o el gestor de la nube.

Cifrado en reposo

  1. 1
    API server--encryption-provider-config
    Lee un archivo EncryptionConfiguration que dice qué recursos cifrar (normalmente Secrets) y con qué proveedores.
  2. 2
    El primer proveedorde la lista
    Cifra todo lo que se escribe. Al leer se prueban todos. identity significa "sin cifrar".
  3. 3
    KMS v2estable desde v1.29
    Cifrado de sobre: una clave de datos cifra el Secret y una clave maestra, que nunca sale del KMS externo, cifra esa clave.
  4. 4
    Secrets viejossiguen en claro
    Solo se cifra al escribir. Hay que reescribirlos: kubectl get secrets -A -o json | kubectl replace -f -.

Auditoría

NivelQué guarda
NoneNada.
MetadataQuién, qué verbo, qué recurso, cuándo y desde dónde. Sin cuerpos. El nivel para Secrets y TokenReviews.
RequestMetadatos y el cuerpo de la petición.
RequestResponseMetadatos, petición y respuesta.
  • Se activa con --audit-policy-file y un destino: archivo (--audit-log-path) o webhook. Sin política no se registra nada.
  • Las reglas se leen en orden y gana la primera que coincide: las específicas van arriba.
  • Etapas: RequestReceived, ResponseStarted, ResponseComplete y Panic.
  • Envía los logs fuera del cluster (a un SIEM): un atacante dentro podría borrarlos.
Trampa

Los Events de Kubernetes no son auditoría: son notas operativas que duran poco (una hora por defecto) y no registran quién hizo cada petición.

Fundamentos de seguridad · 22%

Red: segmentar y cifrar

Por defecto todos los pods se hablan con todos, sin importar el namespace. Las NetworkPolicies cierran eso, siempre que el plugin CNI las aplique (Calico, Cilium y Antrea sí; Flannel solo no).

  • Una NetworkPolicy vive en un namespace y elige pods de ese namespace con podSelector ({} = todos).
  • Son aditivas: lo permitido es la suma de todas las políticas. No hay reglas de "denegar" ni prioridades.
  • Patrón base: denegar todo por defecto y abrir solo lo necesario.
  • Si niegas todo el egress, abre el puerto 53 (UDP y TCP) hacia CoreDNS, o nada resolverá nombres.
  • Funcionan en capas 3 y 4 (IPs, puertos, protocolos). Para reglas por ruta HTTP hace falta un service mesh o políticas L7 del CNI.
  • Los pods con hostNetwork: true quedan casi siempre fuera del alcance de las NetworkPolicies.
Escribes en fromSignifica
namespaceSelector y podSelector en el mismo elementoY: esos pods dentro de esos namespaces.
Dos elementos, cada uno con su guionO: todos los pods de esos namespaces, o esos pods del propio namespace.
ipBlock con exceptRangos de IP, por ejemplo para bloquear 169.254.169.254/32, los metadatos de la nube.

Cifrar el tráfico

mTLS con service mesh

Istio o Linkerd cifran y además verifican la identidad de cada servicio (SPIFFE). En Istio, STRICT exige mTLS y PERMISSIVE acepta también texto plano mientras migras.

Cifrado del CNI

Cilium o Calico cifran todo el tráfico entre nodos con WireGuard o IPsec, sin tocar las apps.

kube-proxy

Solo traduce la IP del Service a IPs de pods. No cifra en ningún modo.

Modelo de amenazas · 16%

Piensa como atacante

Modelar amenazas es mirar el cluster como un mapa de fronteras de confianza y preguntarse qué pasa si alguien cruza cada una. Las que más se preguntan:

Internet → Ingress·Usuario → API server·Contenedor → nodo·Nodo → control plane·Namespace → namespace·Cluster → cuenta de nube
Lo que buscaEjemplo y qué lo frena
PersistenciaUn CronJob o DaemonSet malicioso, un Pod estático en el nodo, un webhook mutante que inyecta un contenedor, un token antiguo guardado en un Secret.
Lo frena: RBAC mínimo, Pod Security, vigilar el audit log.
Denegación de servicioAgotar CPU, memoria, PIDs (fork bomb) o disco; crear miles de objetos; inundar el API server; llenar etcd.
Lo frena: ResourceQuota (también count/…), LimitRange, podPidsLimit, ephemeral-storage, API Priority and Fairness.
Código maliciosoUna app con RCE, una imagen con un minero escondido, una shell que aparece en producción.
Lo frena: No root, sistema de archivos de solo lectura, drop: [ALL], seccomp, imágenes firmadas, Falco.
Atacante en la redARP spoofing con NET_RAW, escaneo de servicios, espiar tráfico, DNS falso.
Lo frena: drop: [ALL], NetworkPolicy por defecto en deny, mTLS con verificación de identidad.
Datos sensiblesEl token en /var/run/secrets/kubernetes.io/serviceaccount/token, secretos en logs o en capas de imagen, etcd y sus backups.
Lo frena: Token solo si hace falta, cifrado en reposo, gestor externo, auditoría en Metadata.
Escalada de privilegiosPod privilegiado con hostPID, hostPath: /, el socket del runtime, verbos RBAC peligrosos, los metadatos de la nube.
Lo frena: Pod Security Restricted, RBAC mínimo, bloquear 169.254.169.254, workload identity.
Trampa

Un pod comprometido puede pedirle credenciales de la nube al servicio de metadatos (169.254.169.254) y saltar del cluster a la cuenta. La respuesta es bloquear ese acceso con egress e IMDSv2 y dar a cada app su propia identidad (IRSA, Workload Identity).

Seguridad de la plataforma · 16%

Cadena de suministro, admisión y PKI

La pregunta de fondo es: ¿cómo sé que lo que corre en mi cluster es lo que construí? Se responde con controles en cada paso, desde el código hasta el runtime.

SBOM

La lista de ingredientes de un software: paquetes, versiones, licencias. Formatos: SPDX y CycloneDX. Con VEX, el proveedor dice si una CVE le afecta de verdad.

Sigstore

cosign firma y verifica imágenes; Fulcio emite certificados de minutos ligados a una identidad OIDC; Rekor es el registro público de firmas.

SLSA

Niveles de confianza sobre cómo se construyó un artefacto. Subir de nivel hace la procedencia más difícil de falsificar.

in-toto

Verifica que cada paso de la cadena lo hizo quien debía, en orden y sin manipulación. Graduado en la CNCF.

Registro

Harbor (graduado en la CNCF): RBAC, escaneo, firmas y replicación. Tags inmutables, imágenes por digest y credenciales de solo lectura.

Escaneo

Trivy o Grype buscan CVEs en la imagen. Hay que volver a escanear lo guardado: aparecen CVEs nuevos después del build.

Observabilidad de seguridad

  • Falco (graduado en la CNCF) mira las llamadas al sistema y alerta cosas como una shell dentro de un contenedor. Detecta, no bloquea.
  • Tetragon (de Cilium) observa con eBPF y puede bloquear en el kernel. Hubble muestra los flujos de red.
  • El audit log responde quién hizo qué en la API. Lo que pasa dentro de los contenedores lo ven Falco o Tetragon.

Service mesh

  • Las identidades son SPIFFE IDs (spiffe://cluster.local/ns/<ns>/sa/<sa>) dentro de certificados; SPIRE las emite fuera del mesh.
  • En Istio: PeerAuthentication decide si se exige mTLS y AuthorizationPolicy decide quién puede llamar qué ruta. istiod firma y rota los certificados.
  • Las políticas del mesh complementan a las NetworkPolicies, no las reemplazan.

PKI del cluster

  • kubeadm guarda las CAs y certificados en /etc/kubernetes/pki. Si roban la clave de la CA, pueden fabricar cualquier identidad.
  • etcd usa una CA separada, para que otros certificados del cluster no sirvan contra etcd. La front-proxy CA es para los API servers agregados.
  • Kubernetes no revoca certificados de cliente: ante una filtración grave, se rota la CA. Por eso se usan certificados de vida corta.
  • La API de CSR pide certificados que se firman tras ser aprobados. Con serverTLSBootstrap, el kubelet obtiene así su certificado de servicio.
  • cert-manager emite y renueva certificados TLS (por ejemplo de Let's Encrypt) y los guarda en Secrets.
  • Konnectivity lleva el tráfico del control plane hacia los nodos por un túnel que abren los propios nodos.

Herramientas

Antes de desplegar

Trivy (imágenes, IaC, SBOM), Checkov o KICS (Terraform y YAML), firmas con cosign.

Al desplegar

Políticas como código: Kyverno, Gatekeeper, ValidatingAdmissionPolicy. En modo auditoría reportan lo que ya existe sin bloquear.

En el cluster

kube-bench (CIS), Kubescape (NSA/CISA y MITRE), Falco y Tetragon en runtime.

Para el día del examen

Reglas que resuelven preguntas

  1. 401 es identidad, 403 es permiso. Autenticación primero, autorización después, admisión al final.
  2. RBAC solo suma. No existe "deny" en RBAC ni en NetworkPolicy estándar: se niega no concediendo.
  3. Crear pods = leer Secrets del namespace. Y list sobre Secrets también es leerlos.
  4. escalate, bind, impersonate y nodes/proxy son vías de escalada.
  5. Base64 no es cifrado. Los Secrets van sin cifrar a etcd hasta que configuras cifrado en reposo en el API server.
  6. Quien toca etcd se salta todo. Solo el API server habla con etcd.
  7. Baseline prohíbe lo de host (hostNetwork, hostPID, hostPath, privileged). Restricted agrega no root, sin escalada, drop: [ALL] y seccomp.
  8. El namespace no aísla. Para código no confiable: nodos dedicados, sandbox (gVisor o Kata) o cluster aparte.
  9. Sin política no hay auditoría. Y los Secrets se auditan a nivel Metadata.
  10. Primero gana en tres lugares: el primer proveedor de la EncryptionConfiguration cifra, la primera regla de auditoría que coincide manda y los webhooks mutantes van antes que los validantes.
  11. Detectar no es prevenir. Falco detecta; la admisión previene; un backup corrige.
  12. kube-proxy no cifra. Cifrado entre servicios: mTLS del mesh o WireGuard/IPsec del CNI.
  13. Los certificados de cliente no se revocan. Para personas, OIDC con tokens cortos.
  14. Si una opción da permisos "por si acaso", usa cluster-admin o comodines *, casi seguro es la incorrecta.

escalate es para crear o editar roles con más permisos; impersonate, para actuar como otro.

S4¿Dónde se configura el cifrado de Secrets en reposo?▸
En el API server, con --encryption-provider-config

etcd solo guarda el resultado cifrado. Con KMS v2, la clave maestra queda fuera del cluster.

S5¿Qué nivel de auditoría usas para Secrets?▸
Metadata

Request o RequestResponse escribirían el valor del secreto en el log.

S6¿Qué hace el puerto 10255 del kubelet y qué hay que hacer con él?▸
Es de solo lectura y sin autenticación: se apaga (readOnlyPort: 0)

La API completa del kubelet está en 10250 y debe exigir autenticación y autorización Webhook.

S7Tras un default deny de egress, los pods no resuelven nombres. ¿Por qué?▸
Falta permitir el puerto 53 hacia CoreDNS

UDP y TCP. El deny bloquea también el DNS.

S8¿Qué combinación de un pod permite escapar al nodo con nsenter?▸
privileged: true y hostPID: true

Entra en los namespaces del proceso 1 del nodo. Baseline prohíbe ambas.

S9Falco alerta una shell en un contenedor. ¿Qué tipo de control es?▸
Detectivo

Avisa, no bloquea. Rechazar un pod privilegiado en la admisión sería preventivo.

S10¿Qué componente de Sigstore emite certificados de corta duración para firmar?▸
Fulcio

cosign firma y verifica; Rekor es el registro de transparencia.

R, Repudiation
